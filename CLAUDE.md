## Two sites in one repo

The repo holds two separate implementations of the same portfolio (Mohamed Adel, Flutter developer), backed by the same Firestore project (`my-website-bf9e6`):

- **`jaspr_site/`** — the **live site** at https://muhammed-adel.web.app. A static-mode Jaspr (Dart) site. This is what CI builds and deploys.
- **repo root (`lib/`, `web/`)** — the original Flutter Web app (WASM). Not what is currently deployed, despite what `README.md` says. `firebase.json` hosting serves `jaspr_site/build/jaspr`.

When asked to change "the site", confirm which one is meant; content/UI changes to the live site belong in `jaspr_site/`.

## Commands

Flutter app (repo root):

```bash
flutter pub get
flutter run -d chrome
flutter analyze                      # lints: flutter_lints + extras in analysis_options.yaml (avoid_print, prefer_final_locals, unawaited_futures, ...)
flutter test                         # all tests
flutter test test/hero_mobile_test.dart   # single file
flutter build web --release --wasm --base-href="/"
```

`test/widget_test.dart` is the untouched Flutter counter template and will fail against the real `MyApp` (which also needs Firebase + `get_it` initialised); don't treat it as a meaningful signal.

Jaspr site (`cd jaspr_site`):

```bash
dart pub get
jaspr serve                          # dev server on http://localhost:8080
jaspr build --sitemap-domain=https://muhammed-adel.web.app   # output: jaspr_site/build/jaspr
```

## Deployment

- `.github/workflows/deploy-firebase.yml`: on push to `main`, installs `jaspr_cli` **pinned to 0.23.2** (0.23.1 fails with a build-daemon error — don't unpin casually), builds `jaspr_site`, deploys to Firebase Hosting channel `live`.
- `.github/workflows/deploy.yml`: publishes a redirect page to GitHub Pages pointing at the Firebase URL. It is not a real build.
- `firestore.rules`: public read everywhere; public write only to `analytics`; content collections (`projects`, `experiences`, `expertise`, `profile_info`, `testimonials`, `why_choose_me`) are write-restricted to authenticated users (an admin dashboard outside this repo).

## Architecture

**Content lives in Firestore, not in code.** Projects, experience, expertise, hero/about/contact copy are fetched at runtime. Both sites read the same collections; `lib/core/constants/app_data.dart` holds static fallbacks/constants for the Flutter app.

### Flutter app (`lib/`)

Feature-first clean architecture. Each `lib/features/<feature>/` (`hero`, `about`, `expertise`, `experience`, `projects`, `contact`, `testimonials`, `why_choose_me`, `home`) is split into `data/` (datasources + models + `*_repository_impl`), `domain/` (entities + abstract repositories) and `presentation/` (Cubit, pages, widgets). Pages are split per breakpoint (`pages/desktop|tablet|mobile`) and picked via `lib/core/responsive/` (`responsive_builder.dart`, `device_type.dart`).

Wiring spans several files:
- `lib/injection_container.dart` registers everything in `get_it` (`sl`) as lazy singletons: Firestore → remote data source → repository → Cubit. Adding a feature means adding its registration here.
- `lib/main.dart` initialises Firebase and DI, then fires every cubit's `load*()` with `unawaited(...)` so first paint isn't blocked on Firestore. It also silences `debugPrint` in release. `TestimonialsCubit`/`WhyChooseMeCubit` are registered but intentionally not loaded because no section renders them yet.
- `lib/core/navigation/app_router.dart` uses `onGenerateRoute` with named routes (`/`, `/home`, `/about`, `/experience`, `/projects`, `/contact`); unknown routes fall back to `HomePage`.
- Theming via `lib/core/theme/` (`ThemeController` is a `ChangeNotifier` driving `themeMode`); `lib/core/services/analytics_service.dart` writes visit stats to the Firestore `analytics` collection.

`.agent/implementation_plans/clean_architecture_refactoring.md` is the original refactor plan; the target tree in it is aspirational, so trust the actual `lib/` layout.

### Jaspr site (`jaspr_site/lib/`)

- `app.dart` + `jaspr_router`; page content in `sections/` (hero, about, expertise, experience, projects, contact).
- `data/*_repository.dart` read Firestore through `data/firestore_rest.dart` (REST, no Firebase SDK) so it works during static generation.
- Platform-split components use the `x.dart` / `x.vm.dart` / `x.web.dart` convention: `.vm` is the server/prerender implementation, `.web` the browser one, and `x.dart` the conditional export. When editing a component with these siblings, keep all three in sync.
- `main.server.dart`, `main.server.options.dart` and `main.client.dart` are entrypoints (the options file is generated by `jaspr_builder`).
- `firebase.json` hosting config sets long-lived caching for images/fonts/video and `no-cache` for JS/HTML.
